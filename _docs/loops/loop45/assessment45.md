#### Gaps that need a decision (gap-unclear)

##### CS-A5 / CS-A10: how many random strings and hostile payloads must the suites run?

**What is not decided**
The acceptance criteria say each of the eight packages round-trips 100,000 random strings (CS-5) and survives 100,000 hostile payloads (CS-10). The test suites run far fewer, and Python, C# and Swift run none for text. C++ is the only package at 100,000 payloads. The big runs (12,000 to 45,000 texts per package in loop 35, millions in the loop 41 audit) were one-off and live in probes that the continuous build does not run. The behavior itself is not in doubt (the audit found no crash and no over-read); the open point is what the suites must guarantee from now on.

| package | random strings in suite | hostile payloads in suite |
|---------|------------------------:|--------------------------:|
| Python | 0 | 0 |
| TypeScript | 4,000 | 30,000 |
| C# | 0 | 0 |
| Java | 20,000 | 60,000 |
| Rust | 3,000 | 30,000 |
| Go | 3,000 | 20,000 |
| Swift | 0 | 0 (time-bounded corpus fuzz only) |
| C++ | 20,000 | 100,000 |

**Options**
- **A — raise every suite to the stated counts**: each package proves 100,000 and 100,000 on every run. Trade-off: adds seconds to every suite (Python's own speed test needs about 30 seconds for 100,000 round trips) against a continuous-build wall time that loops 31 to 34 worked to cut.
- **B — change the criteria to the counts the suites run, plus the audit probes**: for example 3,000 strings and 30,000 payloads per package in every suite (adding the missing tests to Python, C# and Swift), with the large runs kept as a manual probe before a decoder change. Trade-off: the written number drops 30 times; the big run depends on someone running it.
- **C — keep small suites and run the probes on a schedule**: a nightly job runs the audit probes of all eight packages. Trade-off: a new job and its maintenance; a regression shows the next morning, not on the change.

**Recommendation**: B — the suites then match what they test and the three packages with no random test get one; none — genuine product choice if the 100,000 figure matters to the owner.

##### CS-D5: retrain the tables on real messages before the first release tag?

**What is not decided**
The code tables come from public sentences and made-up number messages, not from the owner's real device messages. The owner said to send 100 to 200 real messages before the first release tag. Retraining changes the bytes of every string in all eight packages, which is free only until the first tag exists. The messages have not arrived and no one has decided what happens if they do not.

**Options**
- **A — freeze the current tables and tag**: Ukrainian and Russian text is about 35 percent of today's size on the sentence set. Trade-off: real messages may compress worse and cannot be improved without a second wire break after the tag.
- **B — wait for the messages, retrain, then tag**: sizes measured on real data. Trade-off: the tag waits on the owner; all fixtures and eight packages are regenerated once (tools exist: `scripts/text/train_tables.py`, `emit_tables.py`).
- **C — tag now and add a version byte before any retraining**: no waiting. Trade-off: every string pays one extra byte or a new header design, which weakens the size goal.

**Recommendation**: none — genuine product choice (depends on data only the owner has).

##### CS-D6: confirm or replace the provisional speed limits for Python (40 seconds) and TypeScript (4 seconds)

**What is not decided**
The criteria mark the Python and TypeScript limits as provisional "until the first measurement". The tests still use 40 s and 4 s, and no measured figure is written anywhere in the docs. A limit set far above the real time cannot catch a slowdown of several times.

**Options**
- **A — confirm 40 s and 4 s as final**: nothing changes except the criteria text. Trade-off: a 5 to 10 times slowdown of the string codec passes unnoticed in these two packages.
- **B — measure once and set the limit at about 3 times the measured time (load-aware like the others)**: slowdowns show up. Trade-off: needs a measurement run on the reference machine and a small test edit; a slow shared runner may need a retry.

**Recommendation**: B — the other six packages already guard within about 1 to 4 times the real time.

##### CS-D7: does a large repeated text need a speed guard in Java, C#, Rust and C++?

**What is not decided**
When one 65,535-character text is written in each of 200 or more rounds, Python, TypeScript, Go and Swift keep the encoded bytes of the first round and reuse them; Python and TypeScript have a test that it finishes within one second. Java and C# have no such shortcut (searched), and no package of Java, C#, Rust or C++ has a test of the case. It is unknown whether they finish in a second, because nothing was run. The loop 35 review called the five different shortcuts a Medium maintenance problem and the loop 36 fix only moved their storage.

**Options**
- **A — add the same one-second test for the four packages and see**: if all pass, nothing else changes. Trade-off: a slow package then needs its own shortcut (a sixth copy).
- **B — one shared rule in the walker of each package instead of per-codec shortcuts**: the same text is encoded once per pack call everywhere. Trade-off: touches the pack walkers in eight packages (large change for a rare input).
- **C — accept**: the packet size limit already caps the damage and the input is the caller's own data. Trade-off: a slow case would show up only in the field.

**Recommendation**: A — cheap, and it shows whether B is ever needed.

### Gaps that need a decision (gap-unclear)

##### EC-D1: ESP32 and Pico "packed there equals the vector bytes"

**What is not decided**
The criterion says the ESP32 and Pico builds with parity on must build clean and that "a message packed there equals the vector bytes". Today the ESP-IDF build is build-only (the firmware prints a check result nobody reads), the Pico example only declares a protected scheme and has no check at all, and the byte equality is proven on the host and on emulated Cortex-M3 and big-endian s390x instead. Nobody decided whether that stand-in is what the criterion meant. The builds themselves (0 warnings) run in CI only and were not run on this Mac (loop 44 record).

**Options**
- **A - Accept the stand-in**: the criterion is met by the build plus the emulated runs. You get no new work. Trade-off: a compiler or library difference specific to the real ESP32 or Pico chip would go unseen.
- **B - Add the same check to the Pico example**: the Pico firmware gets the position check used on ESP-IDF, still build-only. Trade-off: small work, still not run on a chip.
- **C - Run on a real board or an emulator for each chip**: the equality is shown where it is claimed. Trade-off: needs hardware or emulators the project does not have.

**Recommendation**: A - the byte format does not depend on the chip (checked on a big-endian and a 32-bit target); or `none - genuine product choice`.

##### EC-D2: A protected session payload is not checked across languages

**What is not decided**
The 8 x 8 cross-language check covers plain protected messages. Sessions have their own cross-language check, but it carries no parity bytes. Each package checks that its own protected session payload is the padded clear bytes plus the reference parity (the same padded bytes and the same reference in all eight), so the eight agree by construction, but no test makes one language read another language's protected session payload. The acceptance criterion for sessions (n = 4, two wrong bytes) is stated per package only.

**Options**
- **A - Leave as is**: sessions with parity are proven per package. No work. Trade-off: a language that pads or orders the bytes differently would be found by a user, not by a test.
- **B - Add one protected session payload to the session cross-language check**: one fixed payload read by every other language, both directions as for the unprotected one. Trade-off: about one more row in the slowest CI job group, and a small edit of each session driver.

**Recommendation**: B - cheap, and the unprotected session had exactly this check added for the same reason; or `none - genuine product choice`.
