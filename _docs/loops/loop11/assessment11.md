### Gaps that need a decision (gap-unclear)

#### U1: Empty list and dictionary elements

**What is not decided**
A `list` whose element reads no bytes (for example `list(bytes(0))`, a never-matching `when` in Python or C#, or a nested `list(list(bytes(0)))`) never stops early: each inner list says "65 535 items" and each item reads nothing. A list-in-list of that kind needs a packet of only 131 070 bytes to ask for 65 535 x 65 535 = 4.3 billion empty items, and each item is stored. I measured it in all five packages (times above); extrapolated linearly that is minutes of CPU and tens of gigabytes of memory per packet, so one hostile packet can stall or crash a receiver. A dictionary is bounded because every entry has a key of at least 2 bytes. `times` got a firm rule in this loop (a round that reads nothing is an error); lists and dictionaries were not in the seven specs. The `bool` and empty-group form is already a construction error by the 2026-10-05 decision (row O5), so what remains is `bytes(0)` (every package) and an element made only of a `when` (Python, C#).

**Options**
- **A — same rule as `times`**: an element that reads 0 bytes is an error value at unpack, in all five packages, with one failing-first test each. Trade-off: a legitimate zero-width element (never useful) is now an error even for a count of 1; wire bytes of useful packets are unchanged; five small changes in the `list` / `dict` element loops.
- **B — refuse at construction**: a scheme whose list or dictionary element can be zero-width is a scheme error. Trade-off: earliest and clearest message, but a `when` element is zero-width only for some packets, so this cannot catch everything and A is still needed for those.
- **C — cap**: limit the total number of list items in one packet. Trade-off: a new limit that is visible to users and still allows long runs of real work.

**Recommendation**: A — it is the rule already decided for `times`, needs no new concept, and stops the amplification at the first empty item.

#### U2: A flag bit whose flag byte was never read

**What is not decided**
In the split form a flag byte is read first and its bits decide later fields. If the flag byte sits inside a `when` that did not match (or in another scope than its bits), the bit finds no byte. Today C#, Java, TypeScript and Rust treat the bit as clear and carry on; Python raises `RuntimeError` out of `unpack` (`python/src/packbin/_unpack.py:261-264`) once split form can be built (AZ-2100). Java and C# also behave differently in a `repeat`: Java reuses the previous round's byte, C# looks in the outer scope. AZ-2100 AC-3 only refuses a bit placed before its byte or a byte missing from the scheme; no ticket covers the conditional case.

**Options**
- **A — refuse at construction**: a flag byte must be an earlier, unconditional field in the same scope as its bits; otherwise the scheme is rejected in all five packages. Trade-off: one more construction rule to write and test everywhere; no packet can then reach the orphan state.
- **B — define "clear"**: every package treats an unread flag byte as 0 (bits clear), Python included, and a test pins it. Trade-off: silent, but consistent and cheap; a mistake in a scheme stays invisible.

**Recommendation**: A — it matches the README rule that a tested field "must already have been read" (`README.md:792`) and the vectors that already refuse forward references.

#### U3: C# integers above 2^53

**What is not decided**
C# unpack turns every number into a `double`, so a `u64` or `i64` above 9 007 199 254 740 992 comes back rounded (for example a 64-bit id). It was already so before this loop; the new count code works around it. No ticket exists, and the other four packages return exact values. Fixing it changes the type of unpacked values (a `double` today, `ulong` / `long` after), which a C# caller could notice.

**Options**
- **A — open a ticket now**: return the exact type for each integer kind. Trade-off: visible change for callers who read the value as `double`.
- **B — document the limit and leave it**: Trade-off: silent rounding stays for 64-bit values.

**Recommendation**: A — silent data loss on valid packets, but not urgent; it can be the next C# ticket.

#### U4: Rust name-based references

**What is not decided**
The Rust construction check that refuses a reference to a field outside the `repeat` / `times` works only when the field is named by a number (`"0"`, `"1"`). The usual map form uses names (`eq("type", ..)`, `sized("payload", "len")`), and those are never checked. The unpack-time guard stops any hang, so the question is only whether the same scheme should be refused or accepted depending on how the field is spelled.

**Options**
- **A — track names per scope**: apply the same scope rule to named references. Trade-off: more code in the construction check; one rule for both spellings, as the vector `when_names_outer_field_in_repeat` states.
- **B — leave numeric-only**: Trade-off: named schemes keep the lenient behaviour of the other four packages until the cross-language rule (row O2) is decided.

**Recommendation**: none — genuine product choice; it depends on how O2 (the cross-language rule) is decided, so ask it together.

#### U5: Rust pack count arithmetic

**What is not decided**
`borrowed_count` in the Rust pack path adds the bias with plain arithmetic. A caller-supplied count near the 64-bit limit panics in a debug build and wraps in a release build (which then ends as an item-count error). This is not network input; the unpack side was hardened with checked arithmetic. The Rust spec title and description are about unpack, and the sibling specs state "pack keeps raising on bad rows" (AZ-2071 Excluded, AZ-2073 Excluded) but AZ-2075 has no such line.

**Options**
- **A — leave it**: pack input is caller-controlled and the failure is a clean error in release. Trade-off: a debug-build panic for absurd counts.
- **B — use `checked_add` like unpack**: tiny change. Trade-off: one more edit in a loop that did not plan pack work.

**Recommendation**: A — no network exposure; record it as out-of-scope.

### Not walked

- Race tests for Python, TypeScript and Rust unpack: their flag state is per call by code reading (`python/src/packbin/_unpack.py:206-210`, `typescript/src/walker.ts` `flagBytes` map created in `unpackBody`, `rust/src/walk/unpack.rs:455`); the Rust shared bit counter at construction is AZ-2082. No hostile angle found.
- `repeat` followed by another field: Python and TypeScript stop the repeat on a zero-progress round and let the next field read the leftover byte; C#, Java and Rust return the trailing-bytes error at once. README line 829 says a field after `repeat` is "eaten as another point", so such a scheme is already discouraged; low blast radius.
- A `times` count equal to 0 with a zero-width body is accepted everywhere (tested in C#, Java); only Rust has no dedicated test for it.
- Java `repeat` / `times` rounds share one `seen` map, so a flag byte read in round 1 is visible in round 2 if round 2 does not read its own (part of U2).
