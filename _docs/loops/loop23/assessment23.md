### Gaps that need a decision (gap-unclear)

#### U24: C++ unbound counted member behind a clear `when` (U11)

**What is not decided**
U11 (loop 22) refuses a `bits`, `packed` or `sized` member with no value when the row gives its count above 0 and the `when` that holds the count is clear. Loop 22 assumed C++ cannot spell "no value". It can: a member written unbound (no member pointer, for example `bits(2, 1)`) is never present. With count 3 and a clear `when`, C++ packs the clear bit `01 00 00` at the top level and in all six nested positions (probe and `novalue_nested_host_tests.cpp`, `packed_bias_novalue_host_tests.cpp`), where TypeScript, Python, Java, C# and Rust refuse. An unbound member is C++'s skip-only field: it can never carry the items the count claims. The refusal would sit in `pack_flag_byte`/`pack_flags` (`cpp/src/core/pack.cpp:68-100`); its flash cost is unmeasured and the margin is 40 B.

**Options**
- **A — refuse in C++**: pack returns `BadValue` at the member, as for a bound member; the three hostile `pack_novalue_count_clear_when_*` cases can then run in C++ with an unbound member. Trade-off: flash-gated in a 40 B margin; if the arm stage goes over, the saving needed is recorded and B applies.
- **B — README exception**: C++ packs the clear bit for an unbound member whatever the count, because an unbound member never holds a value; G4 rewords the skip text. Trade-off: 0 B; one more documented C++ row.
- **C — leave it undocumented**: the README already calls it "an open row". Trade-off: the parity table stays open.

**Recommendation**: B — an unbound member is C++'s "not carried" spelling and cannot hold the items the count claims, and A spends unmeasured flash from a 40 B margin. Go note: Go copies the five's rule. Before AZ-2222 it must settle what "no value" is in a Go struct (recommended: a nil slice or nil pointer is no value, an empty slice is a value with zero items, as C# `null` and an empty list).

#### U25: C++ ids outside the int16 range

**What is not decided**
C++ keeps every id in an int16 table entry. U19 closed `eq` source ids outside 0..32 767. Other ids are still cast without a check. A count id of 65 536 (`times`, `bits`, `packed`, `sized`) wraps to 0 and binds field 0 with no error (probe: `times(1, 65536, ...)` and `bits(1, 65536)` build and pack like count id 0). A count id of -1 builds and validates, then every pack and unpack of the scheme fails with `BadValue` at the member (probe). A field's own id or a `when` anchor above 32 767 wraps too (`u8(65536)` builds as id 0 and passes the order check). The batch report's example `eq(65536, 1)` is refused at HEAD.

**Options**
- **A — builder check for every id**: count ids below 0 or above 32 767, and own ids above 32 767, mark the entry Invalid, as `when()` does (`SchemeInvalid` at construction; a compile error for a `constexpr` scheme). Trade-off: compile-time fold, 0 B expected; flash-gated like U19.
- **B — count ids only**: closes the silent bind, which is the case that does harm. Own ids are labels, and count id -1 already fails at pack. Trade-off: smaller change; the own-id wrap stays.
- **C — README note**: say that ids are 0..32 767 in C++. Trade-off: a silent bind remains possible.

**Recommendation**: A — it is the U19 pattern with no expected flash cost, and it closes F36's sibling holes in one place. Go note: Go uses `int` ids, so only negative ids matter there. If Go names sources by id, it copies the range check from this row.

#### U26: C# dictionary rows and a nested-row group

**What is not decided**
A C# nested-row group (`Field.Group(x => x.In, ...)`) has its own id scope, and in typed rows its own object. In dictionary rows (`BinaryPacker.Pack(scheme, IReadOnlyDictionary)`), pack reads the nested row's names from the outer dictionary. A nested dictionary under the group's name is not read. Probe (`u8 Mode; group In { u8 Mode; u8 X }`): the typed row (outer 1, inner 2, X 3) packs `01 01 02 03`; the dictionary `{Mode: 1, X: 3}` packs `01 01 01 03`, so the inner `Mode` silently takes the outer value; `{Mode: 1, In: {Mode: 2, X: 3}}` throws `'X' (field id 1) has no value`. TypeScript (`{g: {mode, c}}`) and Java `Map` rows take the nested object under the group's name. C# has no public dictionary unpack, so no round trip shows the difference. The README documents neither form for C#.

**Options**
- **A — read the nested dictionary**: C# dictionary pack takes the nested row's names from a dictionary under the group's member name, as TypeScript and Java do and as C# typed rows already mirror. Trade-off: a flat dictionary row for a nested-row group stops packing (a breaking change with an upgrade note), and the collision goes away.
- **B — README line only**: C# dictionary rows are flat for a nested row; a name shared with the outer row cannot be given separately; use typed rows. Trade-off: no code; the silent wrong value stays possible.
- **C — refuse the collision**: keep flat rows and refuse a dictionary pack whose nested row shares a name with the row around it. Trade-off: loud, but a third shape that no other package has.

**Recommendation**: A — it is the TypeScript and Java shape, and it removes a silent wrong value. Go note: Go's map form (if it has one) must take the nested map under the group's name, as TypeScript does. This row settles that.
