# CI/CD pipeline

## Loop-end channel (ordinary product loops)

loop_end_merge: main

Owner decision 2026-10-06: this project closes every product loop on `main`, not on `stage`. `origin` has no `stage` branch (`arduino`, `dev` and `main` only) and none is wanted. The value `main` is this project's own definition; the autodev protocol table lists only `none`, `stage` and `stage+main`.

At every loop close, after smoke PASS (the agent runs the smoke script itself and passes the gate when every step passes: `_docs/04_deploy/deployment_procedures.md` § Loop smoke gate), the local merge on `dev` and the `dev` push, the agent does one more step from the launcher: it fast-forwards `origin/main` to `HEAD` (`git push origin HEAD:main`) and then watches the `test.yml` run on `main` as set in the polling section below. It never force-pushes. If `origin/main` is not an ancestor of `HEAD`, it stops and reports. Pushing `main` publishes nothing: a registry publish happens only on a `v*` tag (`publish.yml`), and a tag is always a separate, explicit owner decision.

## Pipeline

GitHub Actions. `test.yml` runs on every branch push (`branches: ["**"]`, not tags), every pull request, and as a called workflow (`workflow_call`); `scaffold` has `timeout-minutes: 60`, `embedded` 90, `ring` 30. `publish.yml` runs on a `v*` tag: its `test` job calls `test.yml` (read-only token, no secrets), and the `publish` job `needs` it, so a failing test job, `ring` included, skips the publish. `publish` alone has `contents: write` and `id-token: write` (`timeout-minutes: 120` since the loop 26 review, 60 before, because the Go proxy window and the Swift consumer window are 30 minutes each; the Go tag is pushed with that `contents: write` token and the job has a SHA-pinned `actions/setup-go` for the proxy check), and a `concurrency` group `publish-${{ github.ref }}` (no cancel-in-progress) serializes runs of one tag.

The publish job builds and checks every artifact first (`publish-build.sh`; `PACKBIN_BUILD_ONLY=1` runs this phase alone, with no credential and no registry write), then uploads what is not yet published (`publish-upload.sh`). Required targets (NuGet, npm, PyPI, crates.io, Maven Central, vcpkg) need their credential or the run fails before any write; optional targets (PlatformIO, ESP-IDF, Arduino) are skipped with a warning when it is missing. Two final targets follow them: the Go tag `go/vX.Y.Z` at the same commit (`publish-go.sh`, then a `proxy.golang.org` check of up to 30 minutes), so a run that failed on a registry pushes no Go tag; a `go/v*` tag does not match the `v*` trigger, so the tag it pushes starts no run. Then, since loop 26, `swift-check` (`publish-swift.sh`, ADR-005): Swift has no registry and no tag of its own, so it writes a throwaway consumer that depends on `https://github.com/zxsanny/packbin` at exactly `X.Y.Z`, runs `swift package resolve` and `swift build` with the runner's Swift, requires the pin to be the commit of the checkout (another commit fails at once naming both), and retries a failed resolve or build in a fresh scratch for up to 30 minutes (`PACKBIN_SWIFT_WINDOW`, 1800 s); it uploads nothing and creates, moves or deletes no tag. The golden gate sums the byte mismatch over all eight languages (`absent go` when the tree has no `go/`, `absent swift` when it has no `Package.swift` or no `swift/`). Re-running the tag finishes a partial publish and re-checks the proxy. See `packages.md`.

`publish-gate.test.sh` (run by the `scaffold` job; it sources `publish-go.test.sh` for the Go release scenarios and `publish-swift.test.sh`, which sources `publish-swift-gate.test.sh`, for the Swift ones, including a real `swift package resolve` and `swift build` of a consumer against a tagged local bare repository) checks this structure by parsing the workflow YAML with Ruby `yaml`. The `scaffold` job runs the eight suites through `docker compose -f docker-compose.test.yml run --rm <lang>` for csharp, typescript, python, rust, cpp, java, go and swift, and its first step requires `go/go.mod`, `go/*_test.go`, `Package.swift`, `swift/Sources/Packbin`, `swift/Tests/PackbinTests/*.swift` and the golden row. The `go` service is `golang:1.27` running `run-suite.sh go`: `gofmt -l` (0 files), `go vet` (0 findings), `go test -race -count=1 -v`, `TestAC7SpeedRoundTrips` once more without `-race` (the AC-10 bound of 1 s is a production-build bound and the race detector costs about 5x, so the test skips it under `-race`), `FuzzUnpack` for 60 s with `-fuzzminimizetime=0` (a named skip line when the package has no such target), and the dependency check (direct requirements and the modules of every built package are the main module and `golang.org/x/crypto`). The `swift` service (loop 26, AZ-2521) is `swift:6.3.3` running `run-suite.sh swift` on the root `Package.swift`: `swift package resolve`, `swift build -c release` with `-warnings-as-errors` and `-strict-concurrency=complete` (0 warnings; the flags are given here, never in `Package.swift`, where an unsafe flag would make the package unusable as a dependency), the debug tests, `swift test list`, the `FuzzTests` run for 60 s (`PACKBIN_FUZZ_SECONDS`; a run shorter than asked fails), the thread-sanitizer build and run (a reported race fails it; the single-threaded size and speed tests do not run there, and no 1 s bound is asserted), the release speed run (`SpeedTests` and the 1 MiB hostile unpack `FuzzTests/mebibyte`), and the dependency check (exactly one dependency, `swift-crypto`). Its SwiftPM cache is the named volume `swiftpm-cache` (a tmpfs in `docker-compose.publish.yml`) and its build output stays in the container (`PACKBIN_SWIFT_SCRATCH`). In loop 26 step 11 the stage took 620 s in that container on the owner's Mac; its time on the runner is unknown. Every `run-suite.sh <lang>` fails when its manifest is missing (`csharp/*.csproj`, `typescript/package.json`, `python/pyproject.toml`, `rust/Cargo.toml`, `cpp/Makefile`, `java/test.sh`, `go/go.mod`, `Package.swift` and `swift/`): a suite that runs nothing must not pass (AZ-2448 for Go, AZ-2477 for the six, owner decision D6 A of loop 25). Whether a language is published stays the publish gate's decision (`publish-gate.sh` prints `absent <lang>`, AC-15); no publish script calls `run-suite.sh`. Go adds one `go suite` row to `test-results/report.csv` (a compose run took about 120 s) and Swift one `swift suite` row. `run-suite.test.sh` and `report-row.test.sh` test it with fake tools. The `scaffold` job also runs `cpp/embedded/lib.test.sh` (31 checks of the embedded harness: it must report FAIL for a target whose command failed, and the stage must exit 1, AZ-2099; and no script pipes `find` into `head`, AZ-2238) and `ring-wiring.test.sh` (the ring wiring below; `ring-wiring-swift.test.sh` guards the Swift lines as a step of the `ring` job and of the scaffold stage of `scripts/loop-tests.sh`). The gate also includes the vcpkg consumer check (`publish-vcpkg.test.sh`, AZ-2098): it stages the port into a local bare registry with the real `publish-registries.sh`, installs it through the vcpkg of the runner (`VCPKG_INSTALLATION_ROOT`), builds and links `packbin::packbin` and compares the program's output with the golden hex. Since AZ-2232 it also checks that vcpkg refuses the port on `x64-windows` (`supports` is `linux | osx`) and that a request for another 0.x minor is not satisfied (`SameMinorVersion` below 1.0). It adds no pin and no `tool-pins.txt` line: the runner's own vcpkg is used and its version is printed in the log. A missing vcpkg or cmake fails the job in Actions; elsewhere the gate prints `NOT RUN` for the check and ends with `publish gate: no failures, NOT RUN: <checks>`, which is not a pass.

## Cross-language ring (loop 16, AZ-2193)

The `ring` job runs `.github/workflows/language-pair.sh`, the byte hand-offs between the eight packages (the six, Go since loop 24 and Swift since loop 26), on every push and pull request. It is its own check: no `needs`, no `if`, no path or branch filter, no `continue-on-error`, so it runs in parallel with `scaffold` and `embedded` (`timeout-minutes: 30`) and a failing ring fails the run. It runs on the runner itself with the seven toolchains of the per-package suites: `actions/setup-dotnet`, `setup-node`, `setup-python`, `setup-java` (Temurin) and `setup-go` and `rustup` install the versions named in the job env (`RING_DOTNET` 10.0, `RING_NODE` 24, `RING_PYTHON` 3.14, `RING_RUST` 1.98, `RING_JDK` 26, `RING_GCC` 16, `RING_GO` 1.27), `docker pull gcc:16` fetches the C++ compiler image, and `ring-toolchains.sh` fails the job, naming the toolchain, when a version differs from the one wanted. ubuntu-latest has no GCC 16 release (13; 26.04 has 15), so `CXX` is `.github/workflows/ring-cxx.sh`, which runs `g++` from the `gcc:$RING_GCC` image with `-static` (a Debian glibc binary does not always run on the runner's glibc) and the same paths as the host; `PACKBIN_CXX_SYSROOT` is empty, so the macOS sysroot recipe of `language-pair.sh` stays off (owner decision 2026-10-06). `ring-wiring.test.sh` (a `scaffold` step) parses `test.yml` and rejects it when the ring is skipped or hidden, and checks that the `RING_*` versions equal the images of the suite services in `docker-compose.test.yml`; it runs the same check on corrupted copies of `test.yml` (28 at loop 16; the script has 35 `expect_rejected` cases since the Go ones: `RING_GO` against the `go` suite image, the `setup-go` pin, the Go version check in `ring-toolchains.sh`, the Go handoff lines of `language-pair.sh`) and each one must be rejected. `publish.yml` calls `test.yml`, so the ring also gates a `v*` tag publish. Since loop 16 it also runs the `listgroup`, `dictgroup` and `listflags` rings for TypeScript, Python and Java (AZ-2239; the bytes and who takes part are in `_docs/02_document/module-layout.md`, workflows), and a failing pair prints one line naming the producer or the consumer (AZ-2238). Loop 24 (AZ-2449) added Go to every kind's ring both ways with every member: 114 explicit `handoff ... go ...` lines (`user`, `nested`, `boolflag`, `booltrue`, `bitwhen`, `session`, `roundflags`, `roundwhen`, `listgroup`, `dictgroup`, `listflags`, the three `-short` refusals, `pack-session` and the position check), the Go driver `.github/workflows/drivers/handoff-go/` (its own `go.mod` with a `replace` to `go/`) built by `ring-go.sh` (host `go` on CI; on a Mac a host binary cross-built in `golang:${RING_GO}`), and the position loop's `publish-position.sh go`. The scenarios note (fit card 3) expects the ring time to about double; the cap stays 30 minutes until the first run measures it. The end-to-end job is unproven until its first run on the Ubuntu runner: before that only its parts ran, on a Mac (108 Go handoffs were run there by the worker; the first Ubuntu run, with `setup-go` and the host `go` build, has not happened). Since loop 25 the C# and C++ drivers are built once a run into a private `mktemp -d` directory (removed on exit) and called from there; `dotnet run` and a C++ compile on every call had cost about 2 s each (40 and 32 calls, 239 s of the ring became 43 s). A `PACKBIN_CPP_HANDOFF` path given by the caller is still compiled on every call. The Java and Go drivers keep their `/tmp` paths (F24 of the infrastructure review is unchanged for them). Loop 26 (AZ-2522) added Swift to every kind's ring both ways with every member: 136 `handoff` lines with Swift (22 of them Go-Swift), the driver `.github/workflows/drivers/handoff-swift/` (the handoff and `position` programs, on the root package by path; its `Package.resolved` must equal the root's) built by `ring-swift.sh` into a scratch directory outside the repository with the runner's `swift`, or in the `swift:${RING_SWIFT}` image when the runner has none (`RING_SWIFT` 6.3.3, the suite image tag; `ring-toolchains.sh` requires Swift 6.3.3 either way), and the position loop's `publish-position.sh swift`. The step 11 ring of loop 26 passed on the owner's Mac, the Go-Swift hand-offs included; the first run on the Ubuntu runner (its Swift version against `RING_SWIFT`, a cold build of swift-crypto) is unproven. `language-pair.sh` is 494 lines and `ring-wiring.test.sh` 500: the next language needs a table-driven ring or a split.

## Read-only repo in the publish containers

The eight golden-gate containers and the five language builds start only through `publish_container` in `publish-lib.sh`, which passes `docker-compose.test.yml` and then `docker-compose.publish.yml`. The second file mounts the repo at `/src` read-only and replaces `/test-results` with a tmpfs (volumes merge by target; `docker compose run -v` over an existing mount is silently ignored on Compose 2.24.3, so it is not used). A build writes only `artifacts/<lang>`, mounted at `/out/artifacts/<lang>` with `PACKBIN_OUT=/out`; C# packs from a copy of `csharp/` and `README.md`, and TypeScript builds in a copy of `typescript/` (AZ-2103: `npm ci --ignore-scripts && npm run build` there, which reads the npm registry for the locked packages and runs `tsc`, then `npm pack`; a `dist` or `node_modules` in the checkout is removed first), and the gate runs the C# driver (and the TypeScript driver when `node_modules` is absent) from a container-local copy. Nothing a container runs (including `npm ci` and the pip downloads) can change a script, a source file or `.git` that the host runs next with the credentials. Never add `docker-compose.publish.yml` to the test-suite calls: those write `bin`, `obj`, `node_modules` and `target`. `publish-readonly.test.sh` (run by `publish-gate.test.sh`) probes the write refusals in all eight services (`RO_SERVICES` includes `go` and `swift`), hashes the tree before and after the gate and a full build-only run, and fails if the override is dropped. Docker Desktop cannot show Linux file ownership: the first green `scaffold` run on `ubuntu-latest` is the proof that the artifact folders end up owned by the runner user.

## Pins and how to bump them

Since loop 16 the `ring` job also pins `actions/setup-dotnet` (v6.0.0, `a98b56852c35b8e3190ac28c8c2271da59106c68`), `actions/setup-python` (v7.0.0, `5fda3b95a4ea91299a34e894583c3862153e4b97`), `actions/setup-java` (v6.0.1, `de7274f081f381c8f8158605e0321c36c376e2e6`) and `actions/setup-node` (v7.0.0, `820762786026740c76f36085b0efc47a31fe5020`); since loop 24 the `ring` job and the `publish` job also pin `actions/setup-go` (v7.0.0, `b7ad1dad31e06c5925ef5d2fc7ad053ef454303e`, released 2026-07-16; the tag dereferences to that commit). The ring toolchain versions are not in `tool-pins.txt`: they are the job env `RING_*`, kept equal to the suite images by `ring-wiring.test.sh`.

Every non-local `uses:` in `.github/workflows/*.yml` is `owner/repo@<40 lowercase hex commit> # <tag>`, and every tool the publish and test scripts install has one exact version in `.github/workflows/tool-pins.txt` (`name==version` per line: `npm`, `twine`, `platformio`, `idf-component-manager`, `build`, `setuptools`, `pytest`); the TypeScript compiler has no line there, the committed `typescript/package-lock.json` pins it. Since loop 26 it also holds `swift==6.3.3`, the image tag of the `swift` suite (not a pip package; `swift:6` is not a Docker Hub tag). `.github/workflows/tool-pin.sh <name>` prints one version and fails for a name that is not pinned. `publish-lib.sh` (`ensure_tool`), `publish-inside.sh` (the Python build, where the same file is the pip constraints file that holds `setuptools`), `run-suite.sh`, `cpp/embedded/examples.sh`, the npm step of `publish.yml` and the gate tests all read it, so a second copy of a version number is a defect. `publish-gate.test.sh` (through `publish-pins.test.sh`) fails on a tag, a branch, a short or upper-case SHA, a missing tag comment, two SHAs for one action, a literal `npm@<digit>`, and a pin that is missing or has become a range.

- Bump an action: `git ls-remote --tags https://github.com/<owner>/<repo>.git <tag> '<tag>^{}'`. Take the `^{}` (peeled) line when one is listed, otherwise the single line; it is the commit of that tag in that repository (an annotated tag has its own object, the peeled line is the commit behind it). Edit every `uses:` line of that action, in every workflow file, to that SHA and the new tag comment. Paste the lookup output into the commit message.
- Bump a tool: edit its one line in `tool-pins.txt`, then wait for a green `test.yml` (the `scaffold` job installs the pip tools and runs the real `pio pkg pack`, `compote component pack` and the Python build; pytest runs in the suite container). `npm` and the two actions that only the publish job runs are proven by the first `v*` tag run.
- Not covered: the transitive Python dependencies of the tools still float (no hash lock), and `ensure_tool` keeps a tool that is already on `PATH`.

## Post-deploy polling (agent configuration)

enabled: yes
long_running: yes (the `embedded` job alone takes about 40 minutes cold; a green `test.yml` takes 45 to 60 minutes; `ring` runs in parallel, is capped at 30 minutes and has no measured time on the runner yet, so the first run decides whether it changes these figures; since loop 24 the Go suite adds about 2 minutes to `scaffold` and the Go handoffs lengthen `ring`, and a tag run adds up to 30 minutes of Go proxy check inside `publish`; since loop 26 the Swift suite and the Swift gate scenarios lengthen `scaffold` (on the owner's Mac the `swift` stage took 620 s and the full publish gate test 1837 s, against the job's 60-minute limit) and a tag run adds up to 30 minutes of Swift consumer check)
poll_interval_seconds: 90
applies_after: a push of `dev` or `main`, and a push of a `v*` tag
status_tool: the GitHub Actions REST API read with `curl` (no `gh` on the agent host, no token needed: the repository is public)
primary_gate: `test.yml` (jobs `scaffold`, `embedded`, `ring`) on the pushed commit; for a tag, the `publish` workflow run (`test`, then `publish`)
report_to: the chat; on FAIL, `autodev/protocols/ci-fail-triage.md`

There is no deploy host to probe. The test and publish results are the GitHub Actions checks.

### Post-deploy pipeline watch (procedure)

1. Take the pushed commit: `sha=$(git rev-parse HEAD)` for a branch push, or the tag's commit for a tag push.
2. Every `poll_interval_seconds`, read the runs of that commit: `curl -s "https://api.github.com/repos/zxsanny/packbin/actions/runs?head_sha=$sha"` and take `workflow_runs[].name`, `status`, `conclusion`. Unauthenticated calls are limited to 60 per hour per address, so the interval is 90 seconds and each poll makes ONE call: read the run by id (`/actions/runs/<id>`), and fetch its jobs only when the run is terminal. A poll that lists the runs of a sha, reads the run and reads its jobs is three calls and uses the hour's budget in about 20 minutes (loop 15: the watch of the `v0.2.2` publish run hit the limit). A `403` with `x-ratelimit-remaining: 0` means wait for `x-ratelimit-reset`; it is not a test result.
3. Terminal states: `status: completed` with `conclusion` `success` (PASS), or `failure`, `cancelled`, `timed_out` (FAIL). No run for the commit after 5 minutes is a blocked trigger (report it; do not start a run by hand).
4. On FAIL name the failed job (`scaffold`, `embedded` or `ring`; for a tag, `test` or `publish`), read its log through the run page the API returns (`html_url`) and apply `ci-fail-triage.md`: three lines, read only. Do not re-run, re-tag or push a fix without the owner.
5. Report PASS or FAIL in the chat as soon as the run is terminal. Never end a turn with "check CI later".

A `v*` tag push also has uploads to six registries and, since loop 24, the Go tag push and its proxy check (up to 30 minutes inside the 60-minute `publish` timeout); its run is the only proof of the registry-side checks, of the Go release and of the live Swift consumer resolve (see `packages.md`). The Go proxy check and the Swift consumer check each have up to 30 minutes inside the 120-minute `publish` timeout. The `go/vX.Y.Z` tag that run pushes starts no workflow.
