# CI/CD pipeline

## Loop-end channel (ordinary product loops)

loop_end_merge: main

Owner decision 2026-10-06: this project closes every product loop on `main`, not on `stage`. `origin` has no `stage` branch (`arduino`, `dev` and `main` only) and none is wanted. The value `main` is this project's own definition; the autodev protocol table lists only `none`, `stage` and `stage+main`.

At every loop close, after smoke PASS (the agent runs the smoke script itself and passes the gate when every step passes: `_docs/04_deploy/deployment_procedures.md` § Loop smoke gate), the local merge on `dev` and the `dev` push, the agent does one more step from the launcher: it fast-forwards `origin/main` to `HEAD` (`git push origin HEAD:main`) and then watches the `test.yml` run on `main` as set in the polling section below. It never force-pushes. If `origin/main` is not an ancestor of `HEAD`, it stops and reports. Pushing `main` publishes nothing: a registry publish happens only on a `v*` tag (`publish.yml`), and a tag is always a separate, explicit owner decision.

## Pipeline

GitHub Actions. `test.yml` runs on every branch push (`branches: ["**"]`, not tags), every pull request, and as a called workflow (`workflow_call`); `scaffold` (the static checks) has `timeout-minutes: 20`, `suites` (a matrix since loop 30: one job per language, Swift as three parts since loop 31; since loop 34, AZ-2627, seven entries: the short suites share a job, `csharp rust` and `cpp typescript java`, each suite of an entry runs although one before it failed and the job then fails naming them, so the file makes 20 jobs, the number the free plan runs at once) and the eight `publish-gate-*` jobs 45 each (loop 28, AZ-2564; five jobs in loop 31 and eight since loop 32, AZ-2625; one `scaffold` job of 60 before), the three `embedded-*` jobs 90 each (one `embedded` job before loop 31, AZ-2607), `ring` 30. `publish.yml` runs on a `v*` tag in three jobs (loop 30). `precheck` (`contents: read` and `actions: read` only, no secrets, 5 minutes) runs `publish-precheck.sh`, which asks the runs API for a completed, successful `push` run of `.github/workflows/test.yml` of this repository at the tagged commit (the close commit of a loop has two: `dev` and `main`) and writes `green=true` only for such a run; no run, a red or running one, a failed API call or an answer that is not JSON gives `green=false` with the reason printed. `test` (`needs: precheck`, `if: needs.precheck.outputs.green != 'true'`) calls `test.yml` (read-only token, no secrets) only without that proof. `publish` `needs` both and runs on `!cancelled() && precheck succeeded && (test succeeded || (green and test skipped))`, so a red, cancelled or missing test, `ring` included, skips the publish. The guard is `publish-workflow.test.sh` (sourced by `publish-gate.test.sh`): it evaluates the `if` of the test call and of `publish` over every result a needed job can have (not their text) and refuses a copy of `publish.yml` for each rule (25 mutants beside the six older ones: the needs, the `if` conditions, the permissions of `precheck`, its output and step, no `precheck`); `publish-precheck.test.sh` runs the script against a stub `curl` (10 run shapes, a failed call, a non-JSON answer, a bad sha or repository, the request and the token) with 11 mutants, one per condition. `publish` alone has `contents: write` and `id-token: write` (`timeout-minutes: 120` since the loop 26 review, 60 before, because the Go proxy window and the Swift consumer window are 30 minutes each; the Go tag is pushed with that `contents: write` token and the job has a SHA-pinned `actions/setup-go` for the proxy check), and a `concurrency` group `publish-${{ github.ref }}` (no cancel-in-progress) serializes runs of one tag.

The publish job builds and checks every artifact first (`publish-build.sh`; `PACKBIN_BUILD_ONLY=1` runs this phase alone, with no credential and no registry write), then uploads what is not yet published (`publish-upload.sh`). Required targets (NuGet, npm, PyPI, crates.io, Maven Central, vcpkg) need their credential or the run fails before any write; optional targets (PlatformIO, ESP-IDF, Arduino) are skipped with a warning when it is missing. ## Read-only repo in the publish containers

The eight golden-gate containers and the five language builds start only through `publish_container` in `publish-lib.sh`, which passes `docker-compose.test.yml` and then `docker-compose.publish.yml`. The second file mounts the repo at `/src` read-only and replaces `/test-results` with a tmpfs (volumes merge by target; `docker compose run -v` over an existing mount is silently ignored on Compose 2.24.3, so it is not used). A build writes only `artifacts/<lang>`, mounted at `/out/artifacts/<lang>` with `PACKBIN_OUT=/out`; C# packs from a copy of `csharp/` and `README.md`, and TypeScript builds in a copy of `typescript/` (AZ-2103: `npm ci --ignore-scripts && npm run build` there, which reads the npm registry for the locked packages and runs `tsc`, then `npm pack`; a `dist` or `node_modules` in the checkout is removed first), and the gate runs the C# driver (and the TypeScript driver when `node_modules` is absent) from a container-local copy. Nothing a container runs (including `npm ci` and the pip downloads) can change a script, a source file or `.git` that the host runs next with the credentials. Never add `docker-compose.publish.yml` to the test-suite calls: those write `bin`, `obj`, `node_modules` and `target`. `publish-readonly.test.sh` (run by `publish-gate.test.sh`) probes the write refusals in all eight services (`RO_SERVICES` includes `go` and `swift`), hashes the tree before and after the gate and a full build-only run, and fails if the override is dropped. Docker Desktop cannot show Linux file ownership: the first green `scaffold` run on `ubuntu-latest` is the proof that the artifact folders end up owned by the runner user.

## Pins and how to bump them

Since loop 16 the `ring` job also pins `actions/setup-dotnet` (v6.0.0, `a98b56852c35b8e3190ac28c8c2271da59106c68`), `actions/setup-python` (v7.0.0, `5fda3b95a4ea91299a34e894583c3862153e4b97`), `actions/setup-java` (v6.0.1, `de7274f081f381c8f8158605e0321c36c376e2e6`) and `actions/setup-node` (v7.0.0, `820762786026740c76f36085b0efc47a31fe5020`); since loop 24 the `ring` job and the `publish` job also pin `actions/setup-go` (v7.0.0, `b7ad1dad31e06c5925ef5d2fc7ad053ef454303e`, released 2026-07-16; the tag dereferences to that commit). The ring toolchain versions are not in `tool-pins.txt`: they are the job env `RING_*`, kept equal to the suite images by `ring-wiring.test.sh`.

Every non-local `uses:` in `.github/workflows/*.yml` is `owner/repo@<40 lowercase hex commit> # <tag>`, and every tool the publish and test scripts install has one exact version in `.github/workflows/tool-pins.txt` (`name==version` per line: `npm`, `twine`, `platformio`, `idf-component-manager`, `build`, `setuptools`, `pytest`, `pyyaml`); the TypeScript compiler has no line there, the committed `typescript/package-lock.json` pins it. Since loop 26 it also holds `swift==6.3.3`, the image tag of the `swift` suite (not a pip package; `swift:6` is not a Docker Hub tag). `.github/workflows/tool-pin.sh <name>` prints one version and fails for a name that is not pinned. `publish-lib.sh` (`ensure_tool`), `publish-inside.sh` (the Python build, where the same file is the pip constraints file that holds `setuptools`), `run-suite.sh`, `cpp/embedded/examples.sh`, the npm step of `publish.yml` and the gate tests all read it, so a second copy of a version number is a defect. `publish-gate.test.sh` (through `publish-pins.test.sh`) fails on a tag, a branch, a short or upper-case SHA, a missing tag comment, two SHAs for one action, a literal `npm@<digit>`, and a pin that is missing or has become a range.

- Bump an action: `git ls-remote --tags https://github.com/<owner>/<repo>.git <tag> '<tag>^{}'`. Take the `^{}` (peeled) line when one is listed, otherwise the single line; it is the commit of that tag in that repository (an annotated tag has its own object, the peeled line is the commit behind it). Edit every `uses:` line of that action, in every workflow file, to that SHA and the new tag comment. Paste the lookup output into the commit message.
- Bump a tool: edit its one line in `tool-pins.txt`, then wait for a green `test.yml` (the `scaffold` job installs the pip tools and runs the real `pio pkg pack`, `compote component pack` and the Python build; pytest runs in the suite container). `npm` and the two actions that only the publish job runs are proven by the first `v*` tag run.
- PyYAML (`pyyaml==` in `tool-pins.txt`) is the one YAML reader of the CI scripts (loop 82, AZ-3381 to AZ-3386; they ran on Ruby before). ### Post-deploy pipeline watch (procedure)

1. Take the pushed commit: `sha=$(git rev-parse HEAD)` for a branch push, or the tag's commit for a tag push.
2. Every `poll_interval_seconds`, read the runs of that commit: `curl -s "https://api.github.com/repos/zxsanny/packbin/actions/runs?head_sha=$sha"` and take `workflow_runs[].name`, `status`, `conclusion`. Unauthenticated calls are limited to 60 per hour per address, so the interval is 90 seconds and each poll makes ONE call: read the run by id (`/actions/runs/<id>`), and fetch its jobs only when the run is terminal. A poll that lists the runs of a sha, reads the run and reads its jobs is three calls and uses the hour's budget in about 20 minutes (loop 15: the watch of the `v0.2.2` publish run hit the limit). A `403` with `x-ratelimit-remaining: 0` means wait for `x-ratelimit-reset`; it is not a test result.
3. Terminal states: `status: completed` with `conclusion` `success` (PASS), or `failure`, `cancelled`, `timed_out` (FAIL). No run for the commit after 5 minutes is a blocked trigger (report it; do not start a run by hand).
4. On FAIL name the failed job (`scaffold`, a `suites` entry, a `publish-gate-*` job, an `embedded-*` job or `ring`; the "... timing" notice annotation of each suite, gate and embedded job holds its seconds and is readable without a token; for a tag, `test` or `publish`), read its log through the run page the API returns (`html_url`) and apply `ci-fail-triage.md`: three lines, read only. Do not re-run, re-tag or push a fix without the owner.
5. Report PASS or FAIL in the chat as soon as the run is terminal. Never end a turn with "check CI later".

A `v*` tag push also has uploads to six registries and, since loop 24, the Go tag push and its proxy check (up to 30 minutes inside the 60-minute `publish` timeout); its run is the only proof of the registry-side checks, of the Go release and of the live Swift consumer resolve (see `packages.md`). The Go proxy check and the Swift consumer check each have up to 30 minutes inside the 120-minute `publish` timeout. The `go/vX.Y.Z` tag that run pushes starts no workflow. Since loop 30 (AZ-2600) `publish-go.sh` asks the proxy only after the pushed tag shows on an anonymous `git ls-remote` (up to 120 s) and 30 more seconds (`PACKBIN_GO_PROXY_SETTLE`): on `go/v0.3.0` the first request came 1.2 s after the push, the proxy answered `unknown revision` and cached that miss, and the next 38 requests (every 30 s) got the cached answer for 19 minutes (a maintainer of the Go proxy puts the cache at up to about 30 minutes, golang/go#40170). The check itself (`go mod download -json` against `proxy.golang.org` only) is unchanged. The effect is unproven until the next tag; a tag that was already there is not waited for.
