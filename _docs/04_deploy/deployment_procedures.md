# Deployment procedures

1. Tests are green on the commit. `publish.yml` calls `test.yml` on the tagged commit first; the `publish` job needs it, so a red test job publishes nothing. A tag runs the tests once, through `publish.yml`.
2. The golden hex matches in every present language.
3. Push a version tag. GitHub Actions builds and checks every artifact first, then uploads to the six required registries (and the three optional embedded ones whose credential is set); a failed build uploads nothing, and a missing required credential stops the run before any build. When `go/` is in the tree the last step pushes the tag `go/vX.Y.Z` at the same commit (without force) and checks the module through `proxy.golang.org` (`go mod download -json`, up to 30 minutes; ADR-004). A failed registry means no Go tag. When `Package.swift` and `swift/` are in the tree the very last step, `swift-check`, resolves and builds a throwaway consumer of `https://github.com/zxsanny/packbin` at exactly `X.Y.Z` (ADR-005; up to 30 minutes of retries); Swift uploads nothing and gets no tag of its own. `PACKBIN_BUILD_ONLY=1` runs the build phase alone with no credential and no network write.

There is no HTTP health endpoint. The check is the position pack `4001000065cd1d00a3e1110100`.

Re-run: if an upload failed, re-run the tag's `publish.yml` run in Actions (or start a new run for the same tag ref). Registries that already hold the version are skipped with `already published <target> <version>` and the rest is uploaded. The Go tag is found at the same commit and not pushed again (at another commit the run fails naming both commits); the proxy check runs again. The Swift check resolves the same commit again and passes; a tag found at another commit fails it naming both commits. Do not publish by hand and do not move the tag. Two runs for one tag queue, they do not overlap.

Required registries: NuGet, npm, PyPI, crates.io, Maven Central, vcpkg. Final targets (after all others): the Go tag `go-tag`, then the Swift consumer check `swift-check`. A missing credential or a failed upload fails the run. Optional: PlatformIO, ESP-IDF, Arduino. A missing credential skips the target with a `::warning::` and a job-summary line; a failed upload still fails the run. Details: `_docs/04_deploy/packages.md`.

Rollback is unlist or deprecate the published version. Do not force-push the tag. A Go version cannot be unpublished: never delete or move `go/vX.Y.Z` (the proxy and the checksum database remember it); mark it `retract vX.Y.Z` in the `go.mod` of the next version and ship that as the next patch. Swift caches and fingerprints the first content it saw for a version, so `vX.Y.Z` is never moved either; the fix is the next patch (ADR-005).

## Loop smoke gate (library repo; owner decision 2026-10-12)

This repo is a library: there is no site, no local deploy and no URL (`LOCAL_URL: none`). The loop smoke is a bash script, `_docs/loops/loop{NN}/smoke{NN}.md`, that prints `[n/N] title`, `PASS (Ns) <result>` or `FAIL` with the last log lines per step, and ends with `N/M steps passed`.

- **The agent runs the smoke script itself** at the commit that closes the loop (the commit before the close commit; the tree must be clean, which step 1 checks), in the order of the script, every step with stdin from `/dev/null` and a time limit. It trial-runs a new script first and fixes the script, not the check, when the script itself is wrong.
- **All `N/N` steps pass: the gate passes without asking the owner.** The agent writes the result into the `## Result` section of `smoke{NN}.md` (commit hash, `N/N steps passed`, "agent run, owner rule 2026-10-12 in `deployment_procedures.md`") and into the loop record (`smoke: PASS`, `smoke_artifact`), then continues with the loop close commit, the `dev` push and the CI watch of `ci_cd_pipeline.md`.
- **Any step fails (or the script cannot run): the gate does not pass.** The agent stops, reports the failing step with the log lines, diagnoses, and asks the owner before the close commit or any push. A step that is skipped, timed out or edited to pass is a failure; the one exception is a stage that `scripts/loop-tests.sh` skips because nothing it covers changed since the commit where it last passed (below), which the script prints with that commit.
- The script is the same list of checks the CI `test.yml` runs plus the focused loop checks; since loop 26 the suites it mirrors are eight (`csharp`, `typescript`, `python`, `rust`, `cpp`, `java`, `go`, `swift`: the `go` step is `docker compose -f docker-compose.test.yml run --rm go`, `run-suite.sh go`, about 2 minutes with the 60 s fuzz; the `swift` step is `docker compose -f docker-compose.test.yml run --rm swift`, `run-suite.sh swift`, 620 s at loop 26 step 11; check `uptime` first because the Go and Swift speed bounds are timing bounds); it does not replace the CI run on `dev`, which stays the proof for timing bounds (loop 17 and loop 20 lessons).

## Loop test script (owner decision 2026-10-14, AZ-2500)

`scripts/loop-tests.sh` runs the loop's test stages for step 11 and for the loop smoke: `scaffold` (the hermetic shell tests, including `scripts/loop-tests.test.sh`), the eight language suites in their CI containers (`go`, `typescript`, `csharp`, `python`, `rust`, `java`, `cpp`, `swift`; the `swift` stage since loop 26 covers `swift/`, `Package.swift` and `Package.resolved`), `cpp-embedded-arm`, `ring`, `ac10` and `publish-gate`. `--plan` prints which stages would run and why; `--all` runs everything; `--only a,b` picks stages; `--jobs N` sets the parallel width (default 3).

- **Stage selection.** A stage runs only when a file it covers changed since the commit where it last passed here. That commit is a stamp, `test-results/stamps/<stage>` (ignored by git), written only when a stage passes on a clean tree. The changed files are the commits after the stamp, the tracked working tree changes and the untracked files; a stamp that is not an ancestor of `HEAD` runs the stage. What each stage covers is the `covers` function in the script: a language directory covers its own suite (tests included); `fixtures/`, the shared workflow scripts and `docker-compose.test.yml` cover every suite; the ring covers every package's non-test sources, its drivers and `language-pair.sh`; the ARM stage covers `cpp/include`, `cpp/src` and `cpp/embedded`; AC-10 covers `csharp/`.
- **The publish gate is skipped unless the publish path changed:** a `publish*` or `tool-pin*` workflow file, `test.yml`, `run-suite.sh`, a `ring-*` script or a driver (the gate's own test reads them), a compose file, `README.md` or a license file (they are packed), a package manifest, `go.mod`, `go.sum`, `Package.swift`, `Package.resolved`, `fixtures/golden.hex`, or a non-test file added, deleted or renamed in a package directory. CI runs the gate on every push and pull request, so a skipped gate is still proved there.
- **Parallel suites.** The eight suites and the scaffold run at most `--jobs` at a time. A suite that fails in the pool is re-run once alone; the output keeps both results (`PASS on the serial retry`, the first failure's log is kept) and the RESULT line lists it. A stage that fails again alone fails the run. The ARM stage, the ring, AC-10 and the gate run one after the other afterwards: the gate hashes the repository tree, so nothing else may write to it while it runs.
- **The smoke.** `smoke{NN}.md` for the next loops is `bash scripts/loop-tests.sh` plus the loop's own checks. At the close, the stamps written by step 11 make the smoke a run of the stages whose files changed after step 11 (and everything, if `--all` is asked for). A stage skipped as unchanged is printed with its stamp commit; any other skip is still a failure.
- `scripts/loop-tests.test.sh` (hermetic, 14 s, also a step of the `scaffold` job in `test.yml`) tests the selection in a temporary git repository (what each kind of change selects and skips, a dirty tree, an untracked file, a foreign stamp, `--all`, `--only`) and the execution with a fake `docker` (retry, stamps, no stamp from a dirty tree).
