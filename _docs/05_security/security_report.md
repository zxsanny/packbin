**F47: Dict keys cost quadratic CPU under Unicode normalization** (Medium / A06)
- Location: `CollectionUnpack.swift:43-51` reads each key with `readString`, which validates the UTF-8 and builds a `String`, then does `guard entries[key] == nil` and `entries[key] = v` on a `[String: Any]`. Swift `String` hashing and `==` work on the NFC form, so a key that is not already NFC is normalized every time it is hashed and every time it is compared with a key in its probe sequence (Swift's dictionary stores no hashes, so a probe compares keys). Normalization sorts each run of combining marks by combining class. The stdlib does that in quadratic time and puts no bound on the run (Unicode's stream-safe limit of 30 marks is not applied). The typed `unpack` inserts the same keys into two more dictionaries (`typedCollection`, `makeDict`). The design came with the owner ruling of 2026-10-14 that NFC/NFD duplicates are refused ("dict key given twice"). The refusal is correct; the cost of reaching it is the issue.
- Evidence (probe `dictkey`, scratchpad `sec26/probe`, release build of the HEAD sources, macOS arm64; scheme `dict("d", u8)`; each key is 4 digits plus U+0301 and U+0316, classes 230 and 220, alternating, 2 bytes each, so NFC must reorder all of them): one key of 1 000 / 4 000 / 16 000 / 65 000 bytes: 0.19 / 2.2 / 27.6 / 413 ms (four times the length costs 12 to 15 times the time). 4 keys of 65 000 bytes (260 015-byte packet): 3.1 s. 16 keys (1 040 051 bytes): 25.3 s, 25.0 s of user CPU, 11 MB resident. 64 keys of 16 000 bytes (1 MB): 3.25 s. 1 000 keys of 1 000 bytes (1 MB): 0.25 s. Controls: the same 16 keys in ASCII take 4 ms; the same marks already in class order take 2.2 ms for 65 000 bytes. So the cost is the reorder, not the UTF-8 check or the string build.
- Scenario: a Swift server or app unpacks packets from a peer it does not trust, with any scheme that has a `dict` (at the top level, in a group, as a list element). Each 1 MiB packet holds one core for about 25 s, about 250 times the documented worst unpack of 1 MiB (0.12 s, batch 5) and against SW-4's one second for each hostile unpack (four such keys, 260 KB, take 3.1 s). `maxRounds`, `maxSlots` and `maxBytes` do not apply (the dict is one slot and `maxBytes` bounds pack only), and unpack takes a packet of any length. No other package normalizes keys. Swift's `Hasher` is seeded per process, so this is not hash flooding and a collision attack does not apply.
- Remediation (owner decision): (a) refuse a dict key (and so the packet, with the short-packet shape and `needed` 0 that bad UTF-8 gets) that is not in Unicode's stream-safe form, a run of more than 30 non-starters (`Unicode.Scalar.Properties.canonicalCombiningClass != 0`), with a linear scan before the `String` is built. That bounds each reorder at about 30 squared steps and leaves every real key alone. Or (b) bound the key length or the summed key bytes of one call (for example 1 KiB a key). Or (c) find duplicates by key bytes and build the `[String: Any]` once. (c) alone does not remove the cost of inserting into the result. Add a hostile case (`unpack_dict_key_combining_marks`, 65 000 bytes, ≤ 1 s) for Swift and a README line. Linux uses the same stdlib normalization code; not run there (no Docker here).

**F48: The Swift consumer check runs dependency manifests in the credentialed step** (Medium / A03, A08)
- Location: `publish.yml:48-61` runs `publish-registries.sh` with every secret in `env`. The build phase unsets the credentials in a subshell (`publish-registries.sh:112-119`), but the upload phase (`:127` then `publish-upload.sh`) keeps them all. `swift-check` is the last target of the `final` tier (`publish-upload.sh:169`), and `publish-swift.sh` runs `swift package resolve` and `swift build` for a consumer on the runner host (`:83`, `:92`) with the runner's preinstalled Swift (not pinned, batch 9 #1).
- Evidence: SwiftPM compiles each dependency's `Package.swift` and runs it as a process that inherits the environment. On Linux that process has no sandbox (the manifest sandbox is a macOS feature). swift-crypto 4.3.1's own manifest reads `ProcessInfo.processInfo.environment` (`Package.swift:249` at bb4ba815). **F49: The session keys are never wiped, and each pad leaves a copy of the key** (Low / A04)
- Location and evidence: `PackSession` has no `deinit`, so `send` and `recv` (`PackSession.swift:27-28`) are freed unzeroed when the session goes away. `ChaCha20.xor` calls `words(key, nonce)` (`ChaCha20.swift:48-56`), which builds the key as an `[UInt32]` with `map`. The optimized assembly of `words` (`swiftc -O -wmo -emit-assembly`) creates a new `ContiguousArray` buffer for it on the heap, and `xor` releases it without zeroing, so each `pack` and each `unpack` leaves one freed copy of the 32-byte key in the allocator. The 64-byte `pad` is zeroed (`:43-45`). In `fill`, the `s` and `x` arrays never reach the heap in -O (no allocation call in its assembly), so review26 #6's "two arrays per block" is a debug-build cost only. The seed (`:155`) and the HKDF block (`:153`) are wiped as the contract asks; CryptoKit's `SymmetricKey` zeroes its own storage. The doc comment at `:171-172` says the session keeps one buffer of its own for each secret, which is not so for the keys.
- Scenario: a later memory disclosure in the host process, or a core dump, holds copies of a live or past session key. With no tag, the key decrypts and forges every payload of that direction. The contract does not require more than the seed wipe, so this is hygiene.
- Remediation: `deinit { wipe(&send); wipe(&recv) }`. Read the key words in `xor` from `key.withUnsafeBufferPointer` into a 16-word tuple (or zero the `[UInt32]` with `defer`). Correct the doc sentence. Owner: Swift package.

### Observations (loop 26, not counted)
- Trap review of every input-derived computation in unpack: `take` (size ≤ left, so `off` never passes `buf.count`); `readLength` (two bytes, at most 65 535); `sized` (`start + count` after `take`); `bits`/`packed` (`itemBytes` cannot overflow for any `Int`: `c / 8 * width + (c % 8 * width + 7) / 8`; `i * width` is at most 16 times the bytes taken; width 1 or 2, so the mask shift is safe); `u2` (`(slots + 3) >> 2`); `readUInt` (size from the scheme, `&*` shifts); `integer(...)` (`truncatingIfNeeded`); `countOf` (`addingReportingOverflow`); `chargeRound` (`maxSlots - slots` cannot overflow because `slots <= maxSlots`; `sumText` adds as `UInt`); the session's position (`< UInt64.max` checked before `+= 1`) and block counter (`UInt64(counter) + blocks <= 2^32`). Pack: every write is preceded by `room` (11 write sites, `Pack.swift`, `PackCounted.swift`, `CollectionPack.swift`), so `out.count <= maxBytes` and `maxBytes - out.count` cannot overflow; `bits`/`packed` allocate only after the list's count equals the written count; `rowCountAbove0` converts a float with `Int64(x)` only for a whole `x` in (0, 2^63).
- Random-packet run (probe `fuzz`): 24 schemes (the repository's fuzz schemes 1 to 21 of `FuzzSchemes.swift`, plus u64-counted `sized`/`packed`/`bits`, a dict of `u8`, and the sparse `when` round in list items); a type byte from the schemes, then 0 to 64 bytes, a quarter of them 0xFF. Release: 9 304 000 calls in 45 s, 880 745 accepted, 6 561 638 `short_packet`, 1 497 634 `trailing_bytes`, 363 983 `too_many`, slowest 79 ms. Debug: 813 000 calls in 30 s, slowest 39 ms. 0 traps (the process exits 0). Not coverage-guided; CI's 60 s `FuzzTests` run is the gate.
- Recursion: unpack recurses by the scheme (`fields`, `collection` -> `item`), never by the packet, so a packet cannot deepen it. A deep scheme is the scheme author's own, as in Go (Swift task threads have smaller stacks than the main thread).
- Quadratic paths named in the brief, all linear: `seen` is saved and reset by reference for each round and nested row (`let saved = seen; seen = [:]`), so it is never copied; `flagBytes.firstIndex` is bounded by the flag bytes the scheme declares; `rows.map` for each name is one pass over the round's slots; `appendList` (`prev + list`) runs at most once per scope (a `repeat` is the last field of its scope). Time scales with the items: F10 with 16 384 items takes 0.34 s and with 65 535 items 1.41 s.
- `[String: Any]` and `Any`: `scalar` picks the type by metatype identity before any cast, and a Foundation object goes to `foreignScalar` (`NSNumber` by class and `objCType`), so an `NSNumber` is not bridged to both `Bool` and `Int`. The step 11 Linux run passed the `NSNumber` tests (not re-run here). `unboxed` reads through at most 8 optionals. The map walker follows the scheme, so a self-containing `NSMutableDictionary` is read only as deep as the scheme. A single NFD key matches an NFC lookup in a Swift `[String: Any]` (canonical equivalence), where the other seven compare bytes, so a byte-filtering gateway in another language and a Swift reader can disagree about which key a packet holds. This is the documented owner ruling; it matters only for non-ASCII keys. On Linux, Foundation's `NSDictionary` can merge the two forms itself (step 11 defect 4), so the pack-side refusal is best effort there.
- Error text: session errors give lengths only; unpack errors give field ids, names, counts and the type byte, never packet content; pack errors give row integers and Swift type names. A `PackSession.pack` refusal can therefore carry a clear value of the row the caller meant to encrypt, which is for the caller's logs to handle. The package does not print or log anything.
- Session against the contract (probe `session`): RFC 8439 §2.4.2 through the package's ChaCha20 gives `6e2e359a2568f98041ba0728dd0d6981`, as in the RFC. HKDF-SHA256 computed in Python's standard library (seed 00..1f, salt a0..af, info `packbin`, 64 bytes), whose first 32 bytes are the opener's send key, with nonce = position little-endian and block 0, reproduces `PackSession` payloads 0 and 1 byte for byte; the waiter reads the row. Salt, info, lengths, the key order, the counter and the 12-byte nonce match `pack-session.md`. ChaCha20 is ARX with no branch or index that depends on the key or data, and there is no tag (by contract). The opener value comes from `SystemRandomNumberGenerator` (the OS CSPRNG), one 64-bit draw for each byte. A failed pack spends no position; every `unpack` on an open session spends one (as TypeScript and C#). `PackSession` is a non-`Sendable` class in a Swift 6 language-mode module, so a Swift 6 caller cannot share one between tasks without an explicit unsafe opt-out. Go's F43 race is a compile error here, but a consumer in Swift 5 mode gets warnings only.
- Supply chain: `Package.resolved` (root and driver) pins swift-crypto 4.3.1 at `bb4ba815dab96d4edc1e0b86d7b9acf9ff973a84` and swift-asn1 1.7.3 at `3b6410f7dee09eb33cdd26260c5fd47fda19b0e2`. On Apple platforms SwiftPM still clones both packages and runs their manifests (in the macOS manifest sandbox) although nothing is linked (AZ-2518). `Package.swift` declares no unsafe flags, C targets or plugins (`run-suite.sh` `swift_deps` checks it). `publish-swift.sh` writes the version into the consumer manifest only after `check_swift` has required a semantic version at build time and after its own quote, backslash and line-break refusal (`:34-39`). **F51: C++ dict keys cost the square of the entries** (Medium / A06)
- Location and evidence: `check_new_key` compares the key of the entry just read with the key of every earlier entry of the bound `Array<Entry<V, Text<N>>, M>` (`same_key`, a length compare and a `memcmp` of the decoded bytes). The probe `dict-quad` (`fixtures/hostile/fuzz/cpp/`) sends M distinct keys of about 6 bytes: 1,024 entries 4 ms, 4,096 67 ms, 16,384 (98 KB) 1.06 s, 65,535 (393 KB) 16.9 s at load 4 to 5. Equal-length keys with a long shared prefix cost more per pair. Since AZ-2062.
- Scenario: a C++ host binds a dict with a capacity near the u16 count the other seven packages accept (the row is about 0.5 MB at 65,535) and reads packets from a peer it does not trust. Every use in the repository has M at most 8, and an embedded target cannot hold a large M. The auditor rated it High by the brief's "a hostile unpack above 1 s"; the owner rated it Medium on 2026-10-19, as F47 (the same class in Swift, any dict, 25 s per 1 MiB) was rated in loop 26, because it needs a capacity the caller chooses.
- Remediation (owner, next loop): refuse a dict whose decoded keys are not in strictly ascending byte order in all eight packages (every encoder already writes them so, `compact-text.md` invariants), so each key is compared with the one before it only. That is O(M), covers unbound dicts (F56) and removes one more non-canonical form. Until then the contract and the README say to size the capacity to what a peer may send (4,096 entries cost about 70 ms).

**F52: a Rust handler above 32 parity bytes panicked** (Medium / A10)
- Location and evidence: `parity()` is a required method of the public `DispatchHandler` trait (loop 40). `checked_parity` checked the mix and the limit but not the count, and `ecc::unprotect` then sliced the 32-byte syndrome array: "range end index 33 out of range for slice of length 32", reproduced for 33/40, 33/254, 64/64, 254/254 and session 40/60 (declared count / message bytes), debug and release. Go cannot reach it (`Scheme.parity` is unexported and `WithParity` checks it); the other packages refuse a count above 32 when the scheme is built.
- Fix: `ecc::check_limit` refuses `n > MAX_PARITY` with the new `UnpackError::BadParity { parity, max }` before the limit, so no byte is read and no receive position is spent (`a_hand_written_handler_above_32_parity_bytes_is_refused_without_reading`, `a_session_handler_above_32_parity_bytes_is_refused_before_the_receive_index_advances`; both panic without the check). The ring driver maps it to `bad_parity`; `message-ecc.md` (Dispatch) and the README say so.

**F53, F54, F55** (Low, fixed): C# `RequireFits` now applies only with parity (`SessionPack_WithoutParity_TakesAClearMessageAbove254Bytes`, 300 bytes; fails without the guard). Python checks the raw length before the copy and the decode (`test_a_raw_payload_above_65535_bytes_is_refused_for_its_length_before_its_utf8`, `test_a_raw_payload_of_the_largest_count_is_refused_without_a_copy`: a 2,097,151-byte count peaks below 64 KiB, 6.3 MB before). The contract's work bound is restated from the counts of the four arms (Rust 22,800, C# 24,400, Python 28,503 field operations at n = 32, N = 254; under 0.1 ms in every compiled package).
