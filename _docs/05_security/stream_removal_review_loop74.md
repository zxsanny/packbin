# Security review — loop 74, removal of the stream session

**Scope**: `10cc0be..df01e11` on `dev` (intake ff079b6, batches b6a0f73, 0df534e, b86d468, docs df01e11); reviewed read-only on an export of df01e11 (nothing was written in the repository).
**Reviewer**: an independent read-only agent (not the one that wrote the code). Builds and tests ran on the export.
**Verdict**: PASS_WITH_WARNINGS — 1 Low, 5 Info, nothing Critical, High or Medium.

## What was checked

1. **Frame mode unchanged.**
   - Rust: only renames and a struct move (`FrameSession { frame: FrameState }`). Keys are still wiped on drop (`Drop for SlotKeys` → `DirKeys::wipe`, the volatile `wipe`; `MacKey` has its own `Drop`). `mac.rs`, `window.rs`, `session_core/{hkdf,hmac,sha256,wipe}.rs` are not in the diff. The removed `Drop for Session` was `cfg(session)` and wiped only the seed and stream keys; the removed `has_stream_state` guard only stopped one object holding stream and frame state at once. A refused re-load still returns before any state change. `FrameSession` derives neither `Clone` nor `Debug`. Scratch run `cargo test --features frame,ecc --lib frame_`: 12 passed.
   - Java: a null list or null element in `load` gives null; a duplicate counts once; a null direction in `seal`/`open` is `BadValue`, not an exception; the masks are identical to the old ones; `Keys.wipe` covers directions 1 to 3; `ReplayWindow` changed only by moving `Freshness` out.
   - Swift: renames only; the frame concurrency test still runs under the thread sanitizer.
   - None of the 17 deleted session test files had any frame content; the frame and crypto vector files are unchanged.
2. **Moved crypto.** C++ SHA-256, HMAC and the ChaCha20 block are token-identical to the removed `session.cpp`; HKDF is identical up to 8,160 bytes (the old code wrapped its counter after 255 blocks, the new code refuses); `chacha20_xor` guards the counter correctly (0xffffffff with 64 bytes passes, 65 is refused with the data untouched; the 32-bit constant holds on AVR) and its count-down loop fixes the old 16-bit `size_t` wrap. Go bounds (`uint64(counter)+blocks > 1<<32`, HKDF 255 blocks), Python (`_MAX_OKM`, counter checks) and TypeScript (NaN and non-integer refusals) are correct. No crypto module is public: C++ `crypto.hpp` is not installed, Go names are unexported, Python `_crypto` is not in `__all__`, TypeScript `exports` names only `.`. No secret is logged or kept in a global.
3. **Removal completeness.** 0 OS random sources in package sources (getrandom, arc4random, urandom, SecureRandom, getRandomValues, crypto/rand, os.urandom, RandomNumberGenerator); 0 `RandomFn`/`os_random`; the ring, publish and Arduino scripts name `crypto.cpp`; the README mentions `PackSession` only in removal or history notes and tells WebSocket users to use TLS.
4. **Tests.** C++: six broken copies of `crypto.cpp` all caught (counter guard off by one both ways, HKDF limit +32, rotation 7→8, counter not incremented, HMAC long-key threshold +1). Python: 6 of 8 mutants killed; the 2 survivors are equivalent (a looser stream guard is still refused by the block function's own counter check; `_MAX_OKM = 256*32` is still refused by `bytes([256])`), so those refusals are defended twice. Go and TypeScript not run (no `go` on the host; no `node_modules` in the export); their tests read as covering the same boundaries. CI still runs the 5 Rust frame runs, the 7 Java `Frame*` classes and `CryptoVectorsTest`, the whole C# and Swift suites, and the frame vectors and README-example steps.
