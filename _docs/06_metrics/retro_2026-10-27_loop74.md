## Trends against loop 73

- Loop 73 asked to check an owner question's premise before asking: loop 74's owner question came from the owner (is the stream session needed at all?), and the answer was a removal, not a hardening. The lesson is one level earlier: ask what a feature is for before hardening it.
- Loop 73's review caught a wrong premise; loop 74's review caught a lost on-target test of the crypto that moved (F1). Both are things the author of the change did not list.
- The shared-name decision (one set of frame types) found a gap only when a worker compared packages (Swift `Freshness`, Java's empty set): a rename task should diff the public API of all four packages, not trust the list.
- Smoke script quality: in loops 71 and 73 the script also failed on its own parsing at first. This loop four of five script failures were scope errors in its greps. The trial run before the gate remains necessary.

## Top actions

1. Before hardening or porting a feature, ask the owner what it is for (a consumer, an application); a removal is cheaper than a hardening (loop 74 intake).
2. When a feature's tests are deleted, list what only they covered (targets, byte order, integer widths) and re-home it before the commit (security review F1).
3. Keep the logs of a failing smoke step (done in `smoke74.sh`), and ask the app to keep the Mac awake before a long run.
4. Before a rename across packages, diff the public API of all of them against the name list.
