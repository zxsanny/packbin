## Efficiency

- Step 11 ran in 1 384 s (23 minutes) at load 10 to 87, the other sessions of this Mac included. The measured hot spots were the publish gate (706 s), the ring (239 s), the scaffold (112 s) and the Go suite (119 s, 60 s of it the required fuzz). The ring's 239 s was launcher overhead: `dotnet run` (2.2 s) 40 times and a full C++ compile (2 s) 32 times. Building both once a run into a private `mktemp -d` directory gave 43 s (exit 0); `check-cases.sh` went from 4.8 to 2.6 s of CPU per run. The gate stays as it is: caching its package downloads in named volumes would let a poisoned cache persist, which its clean-room design avoids, so the choice is the owner's.
- The first AZ-2472 tests passed without the fix: 3 of 4 count cases and the `when` anchor wrapped to ids another rule already refused. A mutation run in a scratch copy (both hunks reverted: 21 failures) after the rework proved every case.
- The parent read each worker's report against the tree; two things only that read found: the AZ-2472 tests above, and the C# unpack change (U26 A also nests the unpack result), which went to the docs as a breaking change.
- The "STALLED" heartbeat was wrong for the ring and the publish gate: both print only at the end, so a log-growth signal said STALLED while the child processes were changing every few seconds.
- A worker's `cat > /tmp/dummy` waited on stdin for 70 minutes and kept its task alive; the rule was in its prompt. The parent found it when asked why a task had run for an hour, from `ps` and `ListAgents`.

## Lessons

- A ticket key comes from the tracker, never from counting: the first three commits and eight specs named AZ-2452 to AZ-2459, which are existing Jira issues of other work in the shared project; New Task step 7 must create the tickets before any spec or commit uses a key.
- A refusal test passes for the wrong reason unless its input falls into a state that is otherwise valid; make the mutation proof part of the worker's acceptance (revert the fix in a scratch copy, every case must go red) and ask for it in the prompt.
- A launcher that starts a toolchain per call costs minutes when a harness calls it hundreds of times (the ring: 239 s, about 150 s of it `dotnet run` and a recompile); multiply the launch cost by the call count before accepting a harness time, and build once into a private per-run directory.
- A watcher keyed on log growth reports STALLED for a stage that prints only at the end; add a second signal (the child process changes) and check `ps` for old shells when a task outlives the run (a bare `cat` in a worker's shell sat 70 minutes).
