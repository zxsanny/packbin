# Pin everything the credentialed publish job installs

**Task**: AZ-2214_ci_pin_credentialed_job
**Name**: Pin actions by commit and tools by exact version (F12)
**Description**: Every non-local action is a commit SHA, every pip tool and `npm` the publish and test scripts install has an exact version from one file, and a gate test fails on any tag or range that comes back.
**Complexity**: 3 points
**Dependencies**: None (implement before AZ-2215: both edit `publish-inside.sh` and `publish-gate.test.sh`, in different hunks)
**Component**: ci-publish
**Tracker**: AZ-2214
**Epic**: AZ-2069

## Problem

The publish job holds every registry secret and the OIDC request token (`publish.yml:44-57`), and several steps run code that nobody chose a version of:

- Three actions are moving tags: `actions/checkout@v7` (`publish.yml:29`, `test.yml:17`, `test.yml:58`), `actions/setup-node@v7` (`publish.yml:32`) and `NuGet/login@v1` (`publish.yml:37`, a third-party action that receives the OIDC token). A moved tag changes the code of the next release run.
- `npm install -g npm@11` (`publish.yml:36`) is a range: today it resolves to 11.21.0, next month to whatever 11.x is newest.
- Python tools come from PyPI at the version served that day:
  - `ensure_tool` runs `pip install --quiet "$pkg"` with no version (`publish-lib.sh:121-135`, line 132). It is called for `twine`, `platformio` and `idf-component-manager` by `prepare_tools` (`publish-upload.sh:128-140`, lines 133-135, in the step that holds all tokens) and for `platformio` and `idf-component-manager` by the embedded build (`publish-embedded.sh:126-138`, lines 128 and 134, with `MAVEN_GPG_PRIVATE_KEY` in the environment).
  - `python3 -m pip install --quiet build` (`publish-inside.sh:67`) and the isolated build environment of `python3 -m build` fetch `setuptools>=61` (`python/pyproject.toml:12`). A probe on 2026-10-06 showed the build picks setuptools 84.0.0 and records it in the wheel (`Generator: setuptools (84.0.0)`), and that `PIP_CONSTRAINT` overrides the pick (a constraint of 80.9.0 produced a wheel generated by 80.9.0).
- The test side has the same pattern with no secrets in reach: `pip install pytest` in `run-suite.sh:36-39` (line 38), `pip install platformio` in `cpp/embedded/examples.sh:13-16` (line 15), and `pip install platformio idf-component-manager` into the harness venv in `publish-phases.test.sh:100-101`. These are inside AC-L5 ("publish and test scripts") although the audit lists only the publish side.
- Already fine: the Animal Sniffer and ASM jars are pinned by version and SHA-256 (`java/api-check.sh:10-20`); `npm ci` (`publish-position.sh:22-24`) follows `typescript/package-lock.json`, which exists.

Audit evidence: `_docs/05_security/security_report.md` finding F12 (credentialed job) and F1 (moving tags, test side); OSV has no advisory for `twine`, `platformio`, `idf-component-manager` or `build` on 2026-10-06. Likelihood is low (an upstream compromise), impact is every distribution channel, which is why F12 is Medium.

## Outcome

- No workflow `uses:` of a third-party or GitHub action names a tag or branch. Each is a lowercase 40-hex commit SHA followed by a comment with the tag it stands for.
- One file holds every exact tool version (`npm`, the pip tools, `setuptools`, `pytest`). Publish scripts, test scripts, the workflow step and the gate tests read it. A bump is one edit to that file (actions: one SHA per `uses:` line).
- The Python build of the published wheel and sdist uses the pinned setuptools.
- A gate test fails when a non-SHA `uses:` appears in any workflow file, and when a pin goes missing or turns into a range.
- Day one changes no behavior: every pin equals what the moving tag or range resolves to on 2026-10-06.
- Honest limit: this closes the top-level tools and the actions. Their transitive Python dependencies still float (see Flagged concerns); F12 is reduced, not closed.

## Scope

### Included
- `.github/workflows/publish.yml` and `test.yml`: the five `uses:` lines become `owner/repo@<sha> # <tag>` (checkout `# v7.0.1`, setup-node `# v7.0.0`, NuGet/login `# v1.2.0`). The local `uses: ./.github/workflows/test.yml` (`publish.yml:19`) stays.
- Decision, where the tool versions live: one plain text file beside `publish-lib.sh`, one `name==version` line per tool in pip constraints syntax (comments allowed), `npm==11.21.0` included on the same footing. A three-line reader script prints a pin (`<script> twine` prints `7.0.0`; an unknown name fails with a message).
  - Why: every consumer is a bash script, a YAML `run:` step or the Ruby test; none needs a parser beyond "split on `==`".
  - Why not shell variables: `idf-component-manager` has dashes, pip cannot read it as a constraint, and a later frozen dependency list could not be appended to it.
  - Why not a requirements file plus a separate npm number: two places.
  - Why not a lockfile tool (`pip-compile`, `uv`, `poetry`) or pins in `pyproject.toml`: the owner ruled out a new dependency manager, and a pin in `[build-system].requires` ships in the sdist and would force that exact setuptools on every user who builds it.
  - Why a separate reader and not a function in `publish-lib.sh`: `run-suite.sh` (`set -uo pipefail`, no `-e`, `run-suite.sh:2`) must not source a file that turns `-e` on (`publish-lib.sh:2`).
  - The same file can be passed to pip as a constraints file (probed: an entry for a package that is not installed, such as `npm`, is ignored).
- `ensure_tool` (`publish-lib.sh:121-135`) installs `<pkg>==<pin>` with `--only-binary=:all:` into the tools venv. Its "a tool already on PATH wins" rule stays: the tests rely on it for their stubs, and the runner image has none of these tools.
- `publish-inside.sh:62-69`: `build` is installed at its pin, and `python3 -m build` runs with the pins file as `PIP_CONSTRAINT`, so the isolated build environment installs the pinned setuptools.
  - Decision on setuptools: constrain it in the publish build (the pins file), do not touch `python/pyproject.toml`. `setuptools>=61` stays the declared range for people who build the sdist themselves.
  - Not done: `--require-hashes`. It needs every transitive file hash, per Python version and platform; no simple, tool-free way to produce it exists. Recorded as a concern.
- `publish.yml:35-36`: the npm step reads its version through the reader; no literal `npm@<digit>` remains in any workflow.
- Test side: `run-suite.sh:38` (pytest), `cpp/embedded/examples.sh:15` (platformio) and `publish-phases.test.sh:100-101` (the harness venv installs the same pins, with `--only-binary=:all:`) read the same file.
- The structure check inside the existing Ruby `workflow_structure` (`publish-gate.test.sh:302-369`): for every `*.yml` in the workflows directory it is given (a glob, so a new workflow file is covered), every job-level and step-level `uses:` that does not start with `./` must match `owner/repo[/path]@<40 lowercase hex>`; a text pass over the same files requires a `# <tag>` comment after it and one SHA per action across all files; any `run:` text with `npm@<digit>` fails. `docker://` references fail (none exist today).
- Negative proofs on temp copies in a new sibling test file (`publish-gate.test.sh` is 447 lines and `publish-phases.test.sh` is already 500, so new assertions do not go into either; the gate test sources the sibling like it sources `publish-phases.test.sh:430-433`).
- `_docs/04_deploy/ci_cd_pipeline.md`: a short section "Pins and how to bump them".

### Excluded
- The other F12 remediation items: running the build without `MAVEN_GPG_PRIVATE_KEY`, dropping the `PYPI_TOKEN` secret for the OIDC path, `persist-credentials: false` on checkout, installing tools in a step before the credentialed one (`security_report.md` F12 remediation 2 to 4 and the install-step move). Flagged.
- Hash-locked, fully pinned transitive closure; `--require-hashes`. Flagged.
- The Node binary version (`publish.yml:33-34`, `node-version: "24"`), runner label `ubuntu-latest`, container image tags (F3), `arduino-cli` checksum (F2, `examples.sh:25-27`).
- An automatic update bot for the pins.
- Any change to what is published (file names, checks, versions).

## Acceptance Criteria

**AC-1: Every action is a pinned commit**
Given the workflow files in `.github/workflows/`
When the structure check runs
Then all five non-local `uses:` lines (checkout three times, setup-node, NuGet/login) are `owner/repo@<40 lowercase hex> # <tag>`, the same action has the same SHA in every file, and the local reusable call is accepted.

**AC-2: A tag, branch, short or wrong-case reference fails the check**
Given temp copies of the workflows in which one `uses:` is changed to `@v7`, `@v1`, `@main`, a 7-hex abbreviation, a 39-hex string, an upper-case SHA or `docker://alpine:3`, a new step `uses: actions/foo@v1` is added (scenario S12), a SHA is missing its tag comment, or the same action carries two different SHAs
When the structure check runs on each copy
Then it exits non-zero and names the file and the `uses:` value; a copy that adds a new workflow file with a tag fails too.

**AC-3: One file holds exact versions**
Given the pins file
When it is parsed
Then it has exactly one line each for `npm`, `twine`, `platformio`, `idf-component-manager`, `build`, `setuptools` and `pytest`, every line is `name==<digits and dots>` (no range operator, no empty version), and the reader prints each; a name that is not in the file makes the reader fail.

**AC-4: Installs use the pins**
Given the publish and test scripts
When each installs a pip tool (`ensure_tool` for twine, platformio, idf-component-manager; the `build` install in the python build; pytest in `run-suite.sh`; platformio in `examples.sh`; the harness venv) and the workflow installs npm
Then the command carries `<name>==<pin>` read from the pins file (npm: `npm@<pin>`), the tool installs pass `--only-binary=:all:`, and no `pip install` line in `.github/workflows/*.sh` or `cpp/embedded/*.sh` names a package without the reader.

**AC-5: A deliberate bump is one edit (S13)**
Given a copy of the workflow directory in which only the `twine` line of the pins file is changed to another version
When `prepare_tools python` runs against a stub `pip`
Then the stub receives the new version, and with the unchanged file it receives the committed one; nothing else was edited. A new upstream release changes nothing until that line is edited.

**AC-6: The published Python build uses the pinned setuptools**
Given the python build in its container
When `python3 -m build` creates the wheel
Then the wheel's `*.dist-info/WHEEL` says `Generator: setuptools (<pinned version>)`, and the build still produces `packbin-<version>-py3-none-any.whl` and `packbin-<version>.tar.gz`, which `publish-check.py` accepts.

**AC-7: The test jobs use the same pins and still hold no secrets**
Given `test.yml` (jobs `scaffold`, `embedded`)
When they run
Then their checkout is the pinned SHA, pytest and platformio install at the pins, no registry token name appears in `test.yml` (`publish-gate.test.sh:24-29` still passes), and the `contents: read` permission split is unchanged.

**AC-8: The bump procedure is documented**
Given `_docs/04_deploy/ci_cd_pipeline.md`
When an owner wants to bump an action or a tool
Then the document names the pins file and the reader, gives the exact lookup for an action (`git ls-remote --tags https://github.com/<owner>/<repo>.git <tag> '<tag>^{}'`, take the peeled line when one is listed, otherwise the single line, check that it is a commit of that repository's tag), says to edit every `uses:` line of that action together, and says a tool bump is one line of the pins file followed by a green `test.yml`.

## Non-Functional Requirements

**Compatibility**
- Day-one behavior equals today's: each pin is what its tag or range resolves to on 2026-10-06, so the first run after the change publishes the same bytes it would have.
- The pins must work on Python 3.12 (runner) and 3.14 (suite image) and Node 24.

**Reliability**
- A missing or malformed pin fails the install before any tool runs (fail closed), never falls back to "latest".
- Installs still need the network; offline behavior is unchanged.

**Performance**
- No measurable change; `--only-binary` skips sdist builds.

## Constraints

- Canonical path only: pins reach the registry through a tag push → `publish.yml`. No laptop publish, no manual or API-triggered run to prove a pin.
- No force flags: `--break-system-packages`, `--force`, `--legacy-peer-deps` and disabled hash or SSL checks are STOP signals (meta-rule, technology selection); `--only-binary=:all:` is the opposite kind of flag.
- No new dependency manager and no new tool: bash, Ruby `yaml` (already on the runner, Ruby 3.2.3) and pip as today.
- `bash.md`: `#!/usr/bin/env bash`, `set -euo pipefail` in the reader, quoted expansions, no `2>/dev/null`, `shellcheck` and `bash -n` on every changed script.
- 500-line soft cap: no new assertions in `publish-phases.test.sh` (500 lines) or `publish-gate.test.sh` (447) beyond a `source` line and the structure-check change; the edit at `publish-phases.test.sh:100-101` must not add lines to it.
- One canonical path: all consumers read the one file; a second copy of a version number anywhere is a defect.
- Do not edit the audit documents; `_docs/05_security/` is updated by the loop's security step.

## Risks & Mitigation

**Risk 1: A pin does not work on the runner**
- *Risk*: the pins were probed on macOS (Python 3.14) and Linux amd64 under emulation (Python 3.12.15), not on the real runner.
- *Mitigation*: the scaffold job installs them for real before any tag; an install failure is loud (exit non-zero), not silent.

**Risk 2: A transitive dependency ships no wheel for a platform later**
- *Risk*: `--only-binary=:all:` turns an sdist-only release into an install failure.
- *Mitigation*: it fails the scaffold job first, as a visible red build; remove the flag for that tool only after a decision, never silently.

**Risk 3: A SHA is not the commit of the tag its comment names**
- *Risk*: the structure check cannot reach the network, so a mismatch (or a SHA from a fork of the repository, which GitHub also resolves) goes unnoticed.
- *Mitigation*: the bump procedure takes the SHA from `git ls-remote` of the upstream repository's own tag; the implementer pastes the lookup output into the commit message.

**Risk 4: The pins age**
- *Risk*: nothing tells the owner a pinned tool has a vulnerability.
- *Mitigation*: stated, not solved here (Flagged concerns).
