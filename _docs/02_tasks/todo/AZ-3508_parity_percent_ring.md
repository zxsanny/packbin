# Parity percentage rows in the ECC ring and its eight drivers

**Task**: AZ-3508_parity_percent_ring
**Name**: Parity percentage rows in the ECC ring and its eight drivers
**Description**: The cross-language ECC ring compares the eight languages on messages under a parity percentage.
**Complexity**: 5 points
**Dependencies**: AZ-3499_parity_percent_reference, AZ-3500_parity_percent_python, AZ-3501_parity_percent_typescript, AZ-3502_parity_percent_csharp, AZ-3503_parity_percent_java, AZ-3504_parity_percent_go, AZ-3505_parity_percent_swift, AZ-3506_parity_percent_rust, AZ-3507_parity_percent_cpp
**Component**: ECC ring harness (`scripts/ecc`, `fixtures/ecc`, `.github/workflows/ring-ecc*.sh`, the eight ECC drivers)
**Tracker**: AZ-3508
**Epic**: none

## Problem

Each package passes its own vectors, but nothing compares the eight languages with each other under a percentage. A package that rounds the count differently, or finds the clear length wrongly, would pass its own tests and disagree with the others on the wire.

## Outcome

- The ring has rows under percentages 10, 25, 50 and 100: intact, repaired within the message's `n / 2`, refused beyond it, and an impossible length.
- Each of the eight drivers reads the new line form and answers as the reference does; 64 pairs, 0 mismatched.
- A driver that mishandles the new rows turns the ring red naming the rows.

## Scope

### Included
- The ring line form of `fixtures/ecc/README.md` (defined by AZ-3499), the generator rows and the loader in `ring_ecc.py`, `ring-cases.txt`, and the cases of `ring-ecc.test.sh`.
- The eight ECC drivers: `handoff_ecc.py`, `handoff-ecc.ts`, `HandoffEcc.java`, the C# driver, the Go, Rust and Swift handoff projects and `handoff_ecc.cpp`; the C++ driver's source list in `ring-lib.sh` if a core source was added.
- Keep every touched file under 500 lines.

### Excluded
- Any package source, the contract, the vectors; the frame ring; the README.
- Percentages other than the four named.

## Acceptance Criteria

Plan, wording and figures: `_docs/02_task_plans/parity-percent/acceptance_criteria.md` (AC numbers there are noted in brackets), `_docs/02_task_plans/parity-percent/input_data/expected_results/results_report.md` and `_docs/02_task_plans/parity-percent/scenarios.md`.

**AC-1: New rows** [AC-16]
Given `ring-cases.txt` regenerated by `gen_ring_cases.py`
When the ring loads it
Then it has rows under percentages 10, 25, 50 and 100 (intact; repaired at the limit of the message; one wrong byte over the limit; an impossible length; the largest message and one byte above it), the reference confirms each, and the old rows are byte-identical

**AC-2: The real ring agrees**
Given the eight drivers built and started as `ring-ecc.sh` does (python3.14 first on `PATH`)
When the ring runs
Then every pair of the 64 (writer, reader) reports 0 mismatched on the old and the new rows, and each language's refusals match the reference

**AC-3: The rows can fail**
Given a stand-in driver that rounds the count down, or that never lowers a limit, and a one-line mutation of the Go driver
When `ring-ecc.test.sh` and the real ring run them
Then they exit non-zero naming the rows, the mutation is removed afterwards, and the old self-test cases pass unchanged

**AC-4: Existing rows unchanged**
Given the old rows and the old self-test cases
When the change is applied
Then the old rows are byte-identical and the old cases pass
